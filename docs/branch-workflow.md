# 分支工作约定

默认前端为 `frontend-v9`。每个独立需求或修复使用一个分支；一个需求里的前后端代码、测试和必要说明放在同一分支。

## 当前分支

| 分支 | 用途 |
| --- | --- |
| `master` | 稳定基线，验收通过后再合入 |
| `integration/v9` | 汇总所有待验收的 v9 修改，本地联调与试用使用此分支 |
| `feat/v9-question-details` | 题库与组织选题弹窗查看完整题目 |
| `fix/v9-teacher-overview` | 任务统计、组织成员能力等级与画像 |
| `fix/organization-question-bank-isolation` | 原题与训练变体隔离、重复生成复用、正式测评只用原题 |
| `docs/branch-workflow` | 本分支约定与代理工作规则 |
| `backup/v9-before-branch-reorganization` | 拆分前完整提交备份，不用于继续开发 |
| `backup/organization-isolation-stacked` | 原串行题库修复分支备份，不用于继续开发 |

前三个功能分支均从当前 `master` 分出。汇总分支通过合并提交保留各项修改的来源。

## 新需求

开始前检查工作区，已有未提交修改先保留，不覆盖、不带入不相关需求。

```bash
git status --short
git switch master
git switch -c feat/v9-需求名称
# 修复使用 fix/v9-问题名称；说明修改使用 docs/主题名称
# 完成代码与验证后提交，再汇总
git add <本需求的文件>
git commit -m "说明本需求的改动"
git switch integration/v9
git merge --no-ff feat/v9-需求名称
```

没有依赖的新需求从稳定基线创建，避免把汇总分支的全部未验收修改带入新分支。如果需求依赖尚未合入 master 的功能，先写明依赖，再从对应功能分支创建；汇总时先合入依赖。不要为了保持形式上的独立而复制其他需求的代码。

修正同一个尚未验收的需求时回到它的原分支提交，再合入汇总分支；新的独立问题创建新分支。解决合并冲突时保留双方已批准功能，并重新验证汇总结果。不要直接在汇总分支开发功能；合并时必要的冲突处理与跨功能测试适配可以放在合并提交。

## 验收与发布

本地试用保持在 `integration/v9`。所有已汇总需求验收通过后，才将汇总分支合入 `master`；如果只验收部分需求，则仅将对应功能分支合入 `master`。保持合并历史，避免在已共享分支上强制重写历史。

推送、发布和合入稳定分支按用户明确指令执行。本次整理仅修改本地分支，未推送远端。
